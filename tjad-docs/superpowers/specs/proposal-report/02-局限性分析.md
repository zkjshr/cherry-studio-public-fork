# 第二章 局限性分析：仅以"项目资料库"申报为何不足

若本课题仅以"项目资料库"为申报与交付内容，成果将止步于"又一个库"。本章从成果形态、课题定位、应用闭环三个层面论证其三重局限，并给出升维路径。

## 2.1 成果形态局限：被动资产无法直接赋能主业

资料库本质上是"被动资产"：数据躺在库中，价值实现依赖用户主动检索、自行判断、人工整合，赋能链条最后一步仍由人力完成，与设计师"接任务书—找参考—挖文脉—出构思"的实际工作流之间存在结构性断层。我院现状印证了"建库"与"赋能"的分野：EKP 数据管道已实现文档电子化归档与持续自动化入库、累计逾 1.1 万个文档，但现有知识资产以事务性内容为主，面向设计创作的知识——优秀项目设计要点、地域文化档案——尚未结构化沉淀（提案 §一 1.2）。"入库"已做到，再加一库边际价值有限，缺的是从"存"到"用"的转化。外部研究亦表明，知识型员工约 19% 的工时耗费在检索与收集信息上（来源：麦肯锡全球研究院，2012）——瓶颈不在"有没有库"，而在库能否主动进入工作流。

## 2.2 定位局限：技术驱动叙事，验收只能以规模论英雄

"建数据库"是技术驱动叙事：先有数据，再找用途。由此验收只能以数据规模论英雄，无法回答评审最关心的问题——它解决了设计生产中的什么问题？定位不高，创新性论证亦随之薄弱。"存而未用"是行业知识管理的普遍困境：IDC 白皮书转引 AIIM 与福特汽车公司的研究估计，知识型员工 15%–25% 的时间耗费在非生产性的信息相关活动上（来源：IDC，2001）；业界对知识库"沦为杂乱内容的垃圾场"（dumping ground）便告失效的批评亦屡见不鲜（来源：GetSharePoint，2026）。这与我院"知识存而未用、技术与主业连而未通"的判断一致（提案 §一 1.2）。破解之道是以场景为纲："百事通"已确立"能力即服务、知识即服务"的产品架构方向，场景应用即"人设 × 能力 × 知识"的组合配置（提案 §一 1.3），课题定位由"建库"升为"在成熟底座上完成首个场景化应用"。

## 2.3 应用局限：缺少用户触点，价值闭环断裂

资料库没有交互前端，用户触点缺失，使用数据无从谈起；没有使用就没有反馈，没有反馈就无法迭代数据质量——数据资产建设本身也失去了质量改进的闭环。我院现有前端以通用问答为主，尚未形成面向具体设计场景的应用（提案 §一 1.2），若只交付后台资产，等于主动放弃与设计师工作流的接口。升维后的机制恰好补上这一环：灵感助手以百事通官方助手形式分发，桌面端零改动或极小改动（设计 §1）；一期即有 5–10 名试点设计师真实使用（提案 附表 F），活跃用户、对话轮次、产出文档数等使用数据持续回流，"使用—反馈—数据迭代"闭环由此建立。

## 2.4 升维路径：资料库从"交付物"降为"支撑层"

解法是重构交付结构：将资料库从"交付物"降为"支撑层"，将"场景应用 + 数据资产 + 可复制方法论"升为交付物，与三重局限一一对应：百事通前端提供能力入口，解决触点缺失与主业赋能问题；资料库经场景应用转化为直接生产力，解决定位问题；三层注册机制使更换一份组合配置即派生新场景，解决创新性与推广价值问题（提案 附表 D）。相应地，交付口径升为：灵感助手场景应用一项，优秀项目库（≥300 个项目档案）与地域文脉库（≥20 个地区档案及外部来源清单）两项数据资产，方法论论文 2 篇、软件著作权 3–4 项（提案 §五）。资料库不再是课题终点，而是被场景激活、可度量、可迭代的生产要素。
