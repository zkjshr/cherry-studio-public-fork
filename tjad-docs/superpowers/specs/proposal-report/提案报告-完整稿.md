## 第一章 背景

### 1.1 行业背景：存量时代的竞争逻辑与"在地性"要求

政策层面，我国城市建设已明确转向存量更新为主。2025 年 5 月，中共中央办公厅、国务院办公厅印发《关于持续推进城市更新行动的意见》，部署加强既有建筑改造利用、保护传承城市历史文化等八项主要任务[3]。2026 年 5 月，国务院印发《城市更新"十五五"规划》（国发〔2026〕12 号），部署"激活城市存量资源潜力"，提出到 2030 年城市更新行动取得重要进展，要求"保护城市独特的历史文脉、人文地理、自然景观，植根中华优秀传统文化，塑造特色风貌"，"坚决防止大拆大建、拆真建假"，并对历史文化资源开展数字化信息采集和测绘建档[4]。政策导向清晰传递出对地域文脉保护与特色风貌塑造的刚性要求；据此可作合理引申（引申判断，非政策原文表述）：对地域文脉的占有与调用能力，正从方案的"加分项"向承接城市更新业务的"准入项"演变。

行业数据层面，勘察设计行业进入深度调整期。住房城乡建设部《2025 年全国工程勘察设计统计公报》显示：全国具有工程勘察设计资质的企业 26,010 个，同比减少 8.5%；年末从业人员 432.9 万人，同比减少 5.4%；工程设计收入 5,080.8 亿元，同比减少 5.4%；同期企业累计拥有专利 65.5 万项，同比增长 9.3%[5]。增量红利消退、企业数量与收入双降，而行业专利拥有量逆势增长，显示行业正以技术与知识积累对冲规模收缩。在此背景下，前期策划与方案构思环节的竞争权重上升：从行业普遍观察看（专项调研待补充），业主对方案"在地性"的要求趋于提高——方案须回应场地的历史文脉、地域风貌与当代生活。从竞争逻辑看，能在最短时间内调动项目经验与地域知识的团队，更可能在前期竞争中占据先机。

人工智能为上述能力重构提供了新路径。美国建筑师学会（AIA）2025 年 3 月发布的研究显示，约 20% 的建筑事务所正在推进 AI 实施，另有 35% 正在考虑采用，同时从业者对输出可靠性与合规风险仍有顾虑[6]；英国皇家建筑师学会（RIBA）年度 AI 调查亦显示建筑师 AI 采用率持续攀升（2024 年报告：41% 的英国建筑师已在项目中至少偶尔使用 AI；2025 年报告：升至近 60%——以上比例系经二手报道转述，原始报告页待补充）[7]。但通用大模型缺乏企业独家项目知识与结构化地域数据，在知识密集型任务上存在事实性（"幻觉"）风险——该问题域正是检索增强生成研究的出发点（见 §3.2）——检索精度与可信度不足（待补充：大模型检索精度/幻觉率的量化支撑文献）；传统知识管理系统"存而未用"，难以将沉淀知识转化为设计生产力。

### 1.2 企业背景：知识积累初具规模，面向创作的知识尚未沉淀

我院在长期设计实践中积累了大量优秀设计项目、技术规范与工程经验，并通过内部业务系统（EKP）实现文档电子化归档与持续自动化入库，累计入库内部规范、图档、维基文档 1.1 万余份。平台建设方面，已建成基于 WeKnora 的企业知识库平台（生产运行中，支持入库、分块、向量与混合检索）、gateway 服务网关（知识检索、企业鉴权、插件市场分发、模型代理等模块齐备）与"百事通"智能问答前端（基于 Cherry Studio 企业化定制，助手/人格机制、插件市场、对话 UI 均已上线），并以两台 4090 GPU 服务器分别承担 LLM 推理与向量化（提案 §三 3.1）。

然而，现有知识资产以事务性内容为主，面向设计创作的知识——优秀项目的设计要点、项目所在地的地域文化档案——尚未结构化沉淀；前端以通用问答为主，尚未形成面向具体设计场景的应用。知识"存而未用"、技术与主业"连而未通"，正是本课题要解决的问题。

### 1.3 契机："能力即服务"架构确立，场景应用水到渠成

我院智能化客户端"百事通"已确立"能力即服务、知识即服务"的产品架构方向：智能体运行时保持通用，场景应用通过"人设 × 能力 × 知识"的组合配置（preset）快速生成，能力、知识、组合以三层注册机制在 gateway 落地，换一份 preset 即派生一个新场景（设计 §0、§4.1；提案 §一 1.3）。

这意味着本课题不再是"从零开发一个应用"，而是在成熟底座上完成首个场景化应用（灵感助手）与配套数据资产（优秀项目库、地域文脉库）的共建：前端复用既有桌面端、零改动或极小改动，WeKnora 检索引擎不改造，新增能力全部落在 gateway。技术条件、平台条件与数据源条件均已具备（两库的内容资产本身即本课题的建设对象，见 §4.4），正是立项的最佳时机。

条件既备，仍需回答一个申报策略问题：如果只交付一个"项目资料库"，为什么不够？下一章从成果形态、课题定位、应用闭环三个层面给出分析。

## 第二章 局限性分析：仅以"项目资料库"申报为何不足

若本课题仅以"项目资料库"为申报与交付内容，成果将止步于"又一个库"。本章从成果形态、课题定位、应用闭环三个层面论证其三重局限，并给出升维路径。

### 2.1 成果形态局限：被动资产无法直接赋能主业

资料库本质上是"被动资产"：数据躺在库中，价值实现依赖用户主动检索、自行判断、人工整合，赋能链条最后一步仍由人力完成，与设计师"接任务书—找参考—挖文脉—出构思"的典型工作流之间存在结构性断层（该工作流描述系院内经验概括，专项调研待补充）。我院现状印证了"建库"与"赋能"的分野：EKP 数据管道已实现文档电子化归档与持续自动化入库、累计入库 1.1 万余份文档，但现有知识资产以事务性内容为主，面向设计创作的知识——优秀项目设计要点、地域文化档案——尚未结构化沉淀（提案 §一 1.2）。"入库"已做到，再加一库边际价值有限，缺的是从"存"到"用"的转化。外部研究亦表明，知识型员工约 19% 的工时耗费在检索与收集信息上[8]——瓶颈不在"有没有库"，而在库能否主动进入工作流。

### 2.2 定位局限：技术驱动叙事，验收只能以规模论英雄

"建数据库"是技术驱动叙事：先有数据，再找用途。由此验收只能以数据规模论英雄，无法回答评审最关心的问题——它解决了设计生产中的什么问题？定位不高，创新性论证亦随之薄弱。"存而未用"是行业知识管理的普遍困境：IDC 白皮书转引 AIIM 与福特汽车公司的研究估计，知识型员工 15%–25% 的时间耗费在非生产性的信息相关活动上，与 [8] 的估计相互印证[9]；业界另存在知识库因内容芜杂（"沦为杂乱内容的垃圾场"，dumping ground）而失效的批评[10]（该批评的更权威系统性论述待补充）。这与我院"知识存而未用、技术与主业连而未通"的判断一致（提案 §一 1.2）。破解之道是以场景为纲："百事通"已确立"能力即服务、知识即服务"的产品架构方向，场景应用即"人设 × 能力 × 知识"的组合配置（提案 §一 1.3），课题定位由"建库"升为"在成熟底座上完成首个场景化应用"。

### 2.3 应用局限：缺少用户触点，价值闭环断裂

资料库没有交互前端，用户触点缺失，使用数据无从谈起；没有使用就没有反馈，没有反馈就无法迭代数据质量——数据资产建设本身也失去了质量改进的闭环。我院现有前端以通用问答为主，尚未形成面向具体设计场景的应用（提案 §一 1.2），若只交付后台资产，等于主动放弃与设计师工作流的接口。升维后的机制恰好补上这一环：灵感助手以百事通官方助手形式分发，桌面端零改动或极小改动（设计 §1）；一期即有 5–10 名试点设计师真实使用（提案 附表 F），活跃用户、对话轮次、产出文档数等使用数据持续回流，"使用—反馈—数据迭代"闭环由此建立。

### 2.4 升维路径：资料库从"交付物"降为"支撑层"

解法是针对三重局限重构交付结构：将资料库从"交付物"降为"支撑层"，将"场景应用 + 数据资产 + 可复制方法论"升为交付物——百事通前端提供能力入口，合并解决触点缺失（2.3）与主业赋能（2.1）问题；资料库经场景应用转化为直接生产力，解决定位问题（2.2）；三层注册机制使更换一份组合配置即派生新场景，直接回应创新性论证薄弱（2.2），并为成果的全院推广提供机制支撑（提案 附表 D）。相应地，交付口径升为：灵感助手场景应用一项，优秀项目库（≥300 个项目档案）与地域文脉库（≥20 个地区档案及外部来源清单）两项数据资产，方法论论文 2 篇、软件著作权 3–4 项（提案 §五）。资料库不再是课题终点，而是被场景激活、可度量、可迭代的生产要素。

升维路径要成立，一要看院内是否已有可依托的底座，二要看行业技术是否成熟、所谓行业空白是否成立。第三章据此盘点院内平台基础与行业技术现状。

## 第三章 技术现状

### 3.1 院内已具备的平台基础

我院已形成覆盖"前端交互—能力服务—知识存储—数据供给—算力支撑"的完整技术底座，五大核心组件均生产运行（提案 §三 3.1）：

| 组件 | 现状 | 与本课题的关系 |
|---|---|---|
| 百事通桌面端 | 基于 Cherry Studio 企业化定制，助手/人格机制、插件市场、对话 UI 均已上线 | 零改动或极小改动复用为前端，灵感助手以官方助手形式分发 |
| gateway 服务网关 | Python 服务网关，已具备知识检索（kb_search）、WeKnora 代理、企业用户鉴权、插件市场分发、模型代理等模块 | 课题新增能力的宿主，三层注册机制在此落地 |
| WeKnora 知识库 | 生产运行中，支持文档入库、分块、向量检索、混合检索 | 知识存储与检索引擎，不改造，仅新增两个知识库 |
| EKP 数据管道 | 生产运行中，持续自动化入库内部规范、图档、维基文档，已完成 1.1 万余份文档入库 | 建档管道的数据源与工程范式参考 |
| 算力资源 | 两台 4090 GPU 服务器，分别承担 LLM 推理与向量化 | 中期扩容多模态 embedding 的硬件基础 |

百事通已确立"能力即服务、知识即服务"的产品方向：智能体运行时保持通用，场景应用通过"人设 × 能力 × 知识"的组合配置（preset）快速生成（提案 §一 1.3）。架构约束为——桌面端零改动或极小改动，新逻辑全部落在 gateway，WeKnora 不改造（设计 §1 分层架构）。我院虽已通过 EKP 实现文档电子化归档与持续自动化入库，但知识资产以事务性内容为主，面向设计创作的知识（优秀项目设计要点、地域文化档案）尚未结构化沉淀（提案 §一 1.2）。平台能力与知识内容的这一落差，正是本课题的切入点。

### 3.2 行业技术现状

**（一）检索增强生成（RAG）技术已趋成熟。** RAG 由 Meta AI 等机构于 2020 年提出，将非参数化检索向量库与大模型生成相耦合，显著提升知识密集型任务的事实准确性，原始论文已被引用逾 1.9 万次（Semantic Scholar 引用统计，2026-10-13 查询）[11]。Gartner 预测，到 2028 年 80% 的生成式 AI 商业应用将构建于企业既有数据管理平台之上[12]（该新闻稿原文受官网访问限制、未经核对，标题与日期经检索核实，见"引用核验说明"），"企业自有数据 + 检索增强"已成为大模型企业级落地的主流路线；我院 gateway 与 WeKnora 的组合正是该路线的既有工程实现。

**（二）多模态检索技术进入可用阶段。** OpenAI 2021 年发布的 CLIP 模型以对比学习将图文映射至统一向量空间，实现零样本图文匹配，已成为图文检索的基础模型[13]。本课题二期"文脉找图、相似风貌项目"检索即基于此类模型部署，属成熟技术的场景化应用。

**（三）建筑设计行业 AI 应用已现头部实践，但集中于创意表现环节。** 中南建筑设计院自 2022 年 3 月起研发 GIANT AI 平台并于年底全面投入使用，全院近百位设计师参与测试，累计生成效果图方案约 2400 个[14]。行业实践证明设计院具备 AI 工程化能力，但公开案例多聚焦效果图生成环节，面向"项目经验复用 + 地域知识调用"的前期策划场景，据本报告编写时的公开检索尚未见系统化落地的公开案例（该空白判断的核查范围与局限见"附：待落实事项清单"）。

### 3.3 行业差距与本课题差异化定位

对照上述现状，现有技术方案存在三类共性差距（以下为课题提案 §三 3.2 的分析判断，未附外部产品实例与行业综述，代表性实例梳理待补充）：其一，通用大模型助手缺乏企业独家项目知识与结构化地域文脉数据，生成内容泛化不可信；其二，行业知识库产品以文档管理为主，仅支持原始文档检索，无面向设计场景的知识重组与生成能力，知识"存而未用"；其三，学术界文脉研究数字化多为单点研究（某地某要素），缺乏面向设计实务的持续更新数据服务。

本课题差异化定位为三重叠加：**独家内部项目经验（外部不可获取）× 结构化地域文脉库（行业稀缺）× 伴随式场景应用（超越检索问答）**（提案 §三 3.2）。就可行性而言，本课题待补齐环节——设计知识结构化、外部数据合规采集、多模态检索、生图集成——均为成熟技术的场景化集成，总体技术风险可控；遗留的执行性风险与待定事项（数据源逐源合规评估、生图接口形态、试点名单等）见 §7 附表 G 及"附：待落实事项清单"。

底座已在、差距已明，下一章给出完整解决方案。

## 第四章 解决方案

### 4.1 总体思路：以"能力即服务、知识即服务"为方法论主轴

本课题总体思路可概括为"一个主轴、一个应用、两类资产、一套机制"。我院智能化客户端"百事通"已确立"能力即服务、知识即服务"的产品架构方向：智能体运行时保持通用，场景应用通过"人设 × 能力 × 知识"的组合配置（preset）快速生成（提案 §一 1.3）。灵感助手即在该成熟底座上完成的首个官方场景组合，而非从零开发的新应用。

落地层面遵循三条既定架构约束：其一，百事通桌面端（基于 Cherry Studio 企业化定制）零改动或极小改动，灵感助手对用户而言就是一个官方助手（设计 §1；提案 §三 3.1）；其二，新增逻辑全部落在 gateway 服务网关——该网关已具备知识检索、企业用户鉴权、插件市场分发等模块，是课题新增能力的宿主（提案 §三 3.1）；其三，WeKnora 知识引擎不改造，优秀项目库与地域文脉库仅为其新增的两个知识库（提案 §三 3.1）。

机制层面，课题在 gateway 内落地三层注册机制——能力注册表（capabilities）、知识注册表（knowledge_sources）、场景组合表（presets），与既有企业库同范式；灵感助手本身即一份 preset，更换一份 preset 即派生另一场景。此机制是可复制性的直接保证，也是本课题区别于"做一个应用"的方法论价值所在（设计 §4.1；提案 附表 D）。

### 4.2 灵感助手：面向设计前期工作流的伴随式应用

灵感助手以设计任务书为起点，形成六步闭环工作流（设计 §3.1；"任务书上传/粘贴"为入口动作，附表 B 核心工作流将其单独列步，故彼处为七步）：

1. **要素解析**（`parse_brief`）：解析任务书，生成结构化要素卡（功能、地点、规模、风格、约束），交用户确认；
2. **三路检索**（并行）：`search_projects` 检索内部优秀项目库相似项目；`search_region` 检索地域文脉库目标地档案；`search_external` 对未建库地区实时采集补充，生成轻档案并写回；
3. **灵感简报**（`synthesize_brief`）：融合三路素材生成结构化简报，内容全部注明来源；
4. **伴随式深化**：对话式追问、收窄、换向，会话状态显式维护"要素卡＋已采纳方向"，长对话不漂移；
5. **成果沉淀**（`gen_concept_doc`）：生成《项目构思文档》内部版，素材回链；
6. **提案升格**（`upgrade_proposal`）：内部构思成熟后升格为《前期策划提案》对外版，文风切换由人格层完成。

上述"大模型按需调用外部能力"的编排范式具有公开技术依据：ReAct 框架证明大模型交替执行推理与行动可显著提升任务表现与可解释性[15]；Toolformer 研究表明大模型可自主学习调用外部工具的时机与方式[16]；检索增强生成（RAG）则为"模型参数知识之外挂接可更新的外部知识源"提供了成熟范式[11]。

灵感助手共规划 10 项能力端点（含后台建档 `archive_project`、地域采集 `crawl_region`、三期预留的 `gen_image`），均为 gateway HTTP 端点，输入输出由 JSON Schema 声明——Schema 即"能力即服务"的接口契约，亦是上架插件市场的清单（设计 §3.2；提案 附表 B）。

### 4.3 输出三级阶梯

交付成果按能力成熟度分为三级，阶梯随能力上线自然涌现，并非写死的功能档位（设计 §5）：

| 级别 | 内容 | 可用时点 |
|---|---|---|
| L1 检索原始结果 | 三路检索素材包，带引用未加工 | 一期 |
| L2 生成报告 | 灵感简报、构思文档，结构化有叙事线，素材全回链 | 一期 |
| L3 图文＋效果图 | 附实景/风貌图集与 AI 生成意向效果图（严格标注"AI 意向图"，与实景区分） | 二至三期 |

其中 L1 素材包为"结构化数据＋来源清单"的标准产物，一次实现三处复用：用户兜底结果、L2/L3 的输入、建档管道的中间件。

### 4.4 数据资产建设机制

**优秀项目库（内部独家资产）**：对 EKP 历年评优项目原始图档实施 LLM 半自动结构化建档——由大模型抽取草稿档案（设计要点、概念关键词、空间策略标签、图集归类、获奖信息），高置信自动入库，低置信进对话式人工审核队列（置信阈值与判定标准待补充，宜于 M2 建档规模化前确定，附表 G"阈值可调"即指此参数）；档案数据模型含 basic、design、culture、honor、media、source 六类字段，其中 source 保留 EKP 原始文档 ID，保证可溯源（设计 §2.1；提案 附表 C）。

**地域文脉库（外部采集资产）**：采用双层结构——白名单重点地区（首批建库规划 10–20 个，覆盖长三角核心与业务重点城市；建设节奏：M1 先建 5 个、M2 扩至 10–15 个，结题终盘 ≥20 个，见 §4.5 与附表 F）完整建库并季度自动重爬刷新；非白名单地区按项目需要实时采集生成轻档案，高频命中地区自动晋升白名单（"高频"的命中次数阈值待补充，与地域档案 meta.命中次数字段联动，见附表 C.2），晋升机制本身即为课题创新点，其操作标准随阈值一并确定（设计 §2.2）。

**合规采集原则**：外部数据获取遵循"引用优于拷贝"——存储结构化摘要与来源链接，仅白名单地区存全文/图集；只采集公开内容，不触碰登录/付费墙内容；数据源按官方公开、百科知识、学术、UGC/生活、影像五类管理，每源一个采集适配器（adapter），声明覆盖范围、更新频率与合规级别（设计 §2.2、§2.3；提案 附表 E）。该原则与机器人排除协议（robots.txt，RFC 9309[17]）确立的自动化访问边界一致；同时须说明，robots.txt 仅覆盖"网站方声明边界、采集方遵守"这一技术约定，候选 UGC 源（如马蜂窝、小红书）的服务条款、内容版权与个人信息保护要求构成额外合规约束，须纳入 M1 起的逐源合规评估，并已在附表 G 增列对应风险项。

### 4.5 技术路线：三期推进

- **一期（M1–M2，第 1–6 月）文本闭环**：三张注册表与能力框架落地，五项核心能力上线（`gen_concept_doc` 于 M2 上线，见附表 F），灵感简报与构思文档在一期内可用；优秀项目档案由 50 个扩至 200 个，白名单地区由 5 个扩至 10–15 个并上线晋升机制；试点组 5–10 名设计师真实使用；产出方法论论文 1 篇、软件著作权 1–2 项（设计 §6；提案 附表 F）。
- **二期（M3，第 7–12 月）多模态升级**：部署 CLIP 类模型生成图像 embedding[13]，实现"文脉找图""相似风貌项目"图文混合检索；提案升格上线，形成内部构思与对外提案双形态产出闭环；产出论文、软著第二批（设计 §6）。
- **三期（M4，第 13–18/24 月；18/24 双口径系内部文件原载，待院核定，见 §5.3 口径说明）生图集成与全院发布**：`gen_image` 对接公司生图服务；灵感助手切换正式可见性，全院发布；资产终盘目标为优秀项目档案 ≥300 个（建设目标 300–400 个）、地区档案 ≥20 个；完成 2–3 个真实项目效益回访，形成结题材料包（设计 §6；提案 §4.5）。

以上方案如何转化为可验收的成果口径，见第五章。

### 附表 B　能力清单与接口契约

全部 10 项能力为 gateway 上的 HTTP 端点，LLM 以 tool/function 方式调用；输入输出由 JSON Schema 声明——**Schema 即"能力即服务"的接口契约，也是上架市场的清单**（设计 §3.2；提案 §七 附表 B）。

**核心工作流**（首期全文本，能力按需编排的载体，设计 §3.1）：

1. 任务书上传/粘贴；
2. 要素解析 `parse_brief` → 要素卡（功能/地点/规模/风格/约束）→ 用户确认；
3. 检索编排（并行，按需触发）：`search_projects` 检索 WeKnora 优秀项目库（向量+元数据过滤）；`search_region` 检索本地地域档案，未命中则触发补充检索；`search_external` 由爬虫服务按需采集 → 轻档案 → 写回地域库；
4. 灵感简报 `synthesize_brief`（项目解读·参考项目·文脉线索·设计切入方向，全部注明来源）；
5. 伴随式对话（循环）：只重跑需要的环节，会话状态维护"要素卡 + 已采纳方向"；
6. 沉淀 `gen_concept_doc` 《项目构思文档》（内部版），素材回链；
7. 升格 `upgrade_proposal` 《前期策划提案》（对外版），文风切换由人格层完成。

**能力清单与接口契约表**：

| 能力端点 | 功能 | 输入 | 输出 | 依赖 | 上线阶段 |
|---|---|---|---|---|---|
| `parse_brief` 要素解析 | 任务书要素解析 | 任务书文本/文件 | 要素卡 JSON | LLM | 一期 |
| `search_projects` 项目检索 | 优秀项目检索 | 要素卡/自由文本 | 项目档案卡[] | WeKnora | 一期 |
| `search_region` 地域检索 | 地域档案检索 | 地点名/要素卡 | 地域档案或"未建库"标记 | WeKnora | 一期 |
| `search_external` 外部补充 | 外部补充检索 | 检索意图 | 轻档案[]（含来源） | 爬虫服务 | 一期 |
| `synthesize_brief` 简报生成 | 灵感简报生成 | 要素卡+检索结果 | 简报结构 | LLM | 一期 |
| `gen_concept_doc` 构思文档 | 构思文档沉淀 | 会话状态 | Markdown 文档 | LLM | 一期 |
| `upgrade_proposal` 提案升格 | 提案升格 | 构思文档+补充素材 | 提案框架 | LLM | 二期 |
| `gen_image` 意向图（C 预留） | 意向效果图 | 文本/参考图 | 图片 | 公司生图服务 | 三期 |
| `archive_project` 建档（后台） | 项目半自动建档 | EKP 文档 ID | 项目档案草稿 | LLM | 一期（后台） |
| `crawl_region` 地域采集（后台） | 地域采集 | 地区+采集器 | 地域档案/轻档案 | 爬虫服务 | 一期（后台） |

**能力编排关键设计点**（设计 §3.2 关键设计点）：

| 设计点 | 说明 |
|---|---|
| 会话记忆显式化 | 结构化"任务状态"（要素卡+已采纳方向+已用素材），每轮更新；长对话不漂移，文档沉淀有可靠输入 |
| 检索编排是运行时组合 | 三个检索并列注册，由 LLM 工具调用机制按需组合——与"场景=组合"方法论一致 |
| A→B 不返工 | B 阶段仅检索返回变为"文本+图集"，图像 embedding 离线生成，对话链路不变 |
| C 只加不改 | `gen_image` 注册即用 |

**输出三级阶梯**（用户产出随能力注册自然涌现，阶梯同时就是阶段路线图，设计 §5）：

| 级别 | 内容 | 依赖能力 | 可用时点 |
|---|---|---|---|
| L1 检索原始结果 | 三路检索原文素材包：项目档案列表、地域档案原文、外部来源链接，带引用未加工 | `search_*` 三件套 | M1 |
| L2 生成报告 | 灵感简报/构思文档：LLM 融合加工，结构化有叙事线，素材全回链 | + `synthesize_brief` / `gen_concept_doc` | M1–M2 |
| L3 图文+效果图 | L2 基础上附图集 + 生图服务产出的意向效果图 | + 多模态检索 + `gen_image` | M3–M4 |

说明：L1 素材包是标准可复制产物（结构化 JSON + 来源清单），既是用户兜底结果，也是 L2/L3 的输入、建档管道的中间件；L3 效果图严格标注"AI 意向图"（元数据 `provenance: generated`），与项目库实景图区分。

### 附表 C　数据模型

#### C.1 项目档案（优秀项目库，内部独家资产）

项目档案入库 WeKnora，元数据字段即检索维度（设计 §2.1；提案 §七 附表 C）：

```
项目档案 {
  basic:    项目名 / 类型（公建·居住·更新·景观…）/ 地点（省·市·区）/
            规模 / 年代 / 状态（建成·在建·方案）
  design:   设计要点（200字内，LLM 提炼）/ 概念关键词 / 空间策略标签
  culture:  涉及的地域文脉标签（关联地域档案）
  honor:    获奖 / 发表 / 业主评价
  media:    图集（实景·效果图·图纸），B 阶段生成图像 embedding
  source:   EKP 原始文档 ID（可溯源）
}
```

**半自动建档工作流**（知识资产沉淀机制，方法论亮点，设计 §2.1）：

- EKP 原始图档/评优材料 → LLM 抽取草稿档案（结构化字段 + 图集归类）；
- 质量分档：高置信自动入库 / 低置信进人工审核队列（对话式确认，不强求；置信阈值与判定标准待补充，见 §4.4）；
- 入 WeKnora 优秀项目库；抽取复用现有 Qwen 模型管线经验（院内既有管线经验，出处见文献[2] §2.1）；
- **不复用现有 WeKnora 原始文档**（多为内部事务性内容），全部重新结构化整理。

#### C.2 地域档案（地域文脉库，外部资产）

地域文脉库采用双层结构（设计 §2.2；提案 §四 4.4）：

- **白名单重点地区**（首批建库规划 10–20 个：长三角核心 + 业务重点城市；建设节奏：M1 建 5 个、M2 扩至 10–15 个、结题终盘 ≥20 个，见附表 F）：完整本地档案，季度自动重爬刷新；
- **按需补充**：任务书涉及非白名单地区时实时爬取 → 轻档案（结构化摘要 + 来源链接）→ 高频命中地区自动晋升白名单（晋升机制本身是课题创新点；"高频"阈值待补充，见 §4.4）。

地域档案数据模型（设计 §2.2；提案 §七 附表 C）：

```
地域档案 {
  geo:      行政区划码 / 名称 / 层级（省·市·县）
  history:  历史沿革（时间线）/ 城市演变 / 文脉叙事线
  culture:  文化要素（非遗·特产·民俗·地名典故，各带来源链接）
  fabric:   建成环境特征（格局·街巷尺度·材料·色彩·典型风貌元素）
  media:    风貌图集（B 阶段图像 embedding）
  meta:     来源清单 / 最近更新时间 / 命中次数（晋升白名单依据）
}
```

### 附表 D　三张注册表

三层注册机制落地为 gateway SQLite 三张注册表，与 enterprise 库同范式（设计 §4.1；提案 §七 附表 D）：

| 注册表 | 字段结构 | 作用 |
|---|---|---|
| 能力表 `capabilities` | id / name / category（检索·生成·采集·建档·图像）/ endpoint / input_schema / output_schema / requires / modality / status（draft·published·deprecated） | 能力定义：端点、输入输出 Schema、依赖、模态、状态 |
| 知识表 `knowledge_sources` | id / name / kind / kb_id（WeKnora 知识库 ID）/ metadata_fields / access（official·pilot·internal）/ stats（docs·last_synced，资产规模指标自动统计） | 知识库登记：kb_id、可过滤元数据字段、访问级别、资产统计 |
| 组合表 `presets` | id / name / persona（system_prompt·model·temperature）/ capabilities[] / knowledge[] / opening / visibility（official·pilot·draft） | 场景组合：人设 + 能力集合 + 知识集合 + 可见性 |

**灵感助手即一份 preset**——三行注册记录引用的集合；换一份 preset 即另一个场景（如"规范问答助手"）。结题时这是"可复制性"的直接证据（设计 §4.1）。

**市场衔接与权限**（设计 §4.2）：

- preset 下发自动生成官方助手条目，走现有 assistants 分发；
- 上架复用插件市场范式（gateway 目录即货架，scp 上架，无管理端写接口），manifest 扩展 `capabilities[]`、`presets[]` 组件类型；
- 权限：试点期 `visibility: pilot` + 试点组名单（复用 enterprise 用户/token 机制）；验收时切 `official` 即全院发布。

**运行时拼装（一条消息的生命周期）**（设计 §4.3）：客户端带 assistant id 调 gateway /chat（现有链路）→ 查 presets 取组合 → capabilities 注入本轮 tool 列表 → knowledge 决定 kb_search 允许范围 → persona 组装上下文 → LLM 按需调用能力端点 → 流式返回。客户端感知只是"一个功能很多的助手"，端上零改动或极小改动。

### 附表 E　数据源矩阵与合规策略

首期候选数据源矩阵（做成可注册的采集器清单，设计 §2.3；提案 §七 附表 E）：

| 类别 | 候选源 | 用途 | 合规级别 |
|---|---|---|---|
| 官方公开 | 政府文旅/规划网站、地方志数字化平台、文保名录 | 历史沿革、风貌、文保要素 | 可全文采集（限白名单地区） |
| 百科知识 | 维基/百度百科（引用链接） | 快速背景补充 | 仅摘要+引用链接 |
| 学术 | 公开论文摘要（知网只引题录不碰付费内容） | 深度文脉研究线索 | 仅题录/摘要+引用链接 |
| UGC/生活 | 马蜂窝、小红书公开页（摘要+链接） | 特产、当代生活气息 | 仅摘要+引用链接 |
| 影像 | 公开图库/政府风貌图集（具体候选源待核实） | 风貌图集 | 注明版权 |

> 注：表中"官方公开""百科知识""学术""UGC/生活"各类候选源与"长三角"区域范围，经检索核验确认其为真实存在的公开平台或官方区域概念（核验来源见参考文献[27]–[34]）；该核验仅确认平台/区域的存在性，各源内容可否采集、以何合规级别采集，以 M1 起的逐源合规评估结论为准。UGC 类源的服务条款、版权与个人信息合规风险已列入附表 G。"影像"类候选源在设计文件中为泛称，具体图库/图集名称按本章"待定事项"于 M1 起逐源合规评估时落实。

**数据获取原则**（设计 §2.2；提案 §七 附表 E）：

- **引用优于拷贝**：存"结构化摘要 + 来源链接"，仅白名单地区存全文/图集；
- **只爬公开内容**，不碰登录/付费墙；
- 每个数据源一个 adapter，声明覆盖范围/更新频率/合规级别——采集器本身也在能力注册框架内，方法论自洽；
- 白名单地区季度自动重爬更新，来源全程可溯。

### 附表 G　风险预案

（设计 §7；提案 §七 附表 G）

| 风险 | 对策 |
|---|---|
| 外部数据源质量参差 | adapter 合规分级 + 白名单人工抽检 |

- 数据源 adapter 的逐个合规评估，M1 起滚动进行；
